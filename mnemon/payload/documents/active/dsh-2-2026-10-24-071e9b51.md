# DSH 用量「差 2 倍」排查（2026-10-24 快照）

## 结论

1. **不存在「价格表算错 2 倍」，也不是 dsh-context 偷改扣费。** 用户看到的约 0.71 与账户 1.46 属于**不同分母**（单轮 / 单会话 / 仅主会话 vs 全天全账户余额净扣），相除必然得到任意倍数。
2. **账本里不存在 0.71 这个数**：两日全量 156 条 `events[]` 中单轮最大 0.6161332（10-23 17:27:55），10-24 单轮最大 0.199（后为 0.483）。接近 0.71 的只有窄口径：单会话 `session-9373e093` 累计 0.660、仅主会话合计 0.481。
3. **「约 2 倍」的真实来源是子代理**：194 个会话中 186 个 `origin:"subagent"`；成本占比 10-23 为 43.6%、10-24 为 58.6%。任何只显示主会话的界面天然少算一半以上。
4. **峰时溢价可排除**：10-24 是周六，全天走谷价，`isPeakTime` 峰时 ×2 当日从未触发；10-23（周五）峰时溢价仅 +18.6%（3.926242 vs 全谷价 3.618175）。
5. **成本结构（10-24 00:00–01:01）**：缓存命中输入占 token 91.1% 但只占费用 8.5%；未命中输入 5.3% → 24.6%；输出 3.6% → **67.0%**。即钱主要花在输出 token 与子代理上。

## 三层账（同源不同口径）

| 口径 | 时间窗 | 金额 | 字段 |
|---|---|---|---|
| ① 余额净扣（权威） | 00:00:20→11:06:18 | ¥1.46（后为 1.47、2.48） | `.dshw-usage.json` → `accounting.books[scope].days[day].openingUnits−lastUnits`，`SCALE=1e8` |
| ② 逐请求事件累加 | 00:00:04→01:01:25，37 条 | ¥1.138990 | 顶层 `events[].cost` 求和（事件不在 `book.events` 内） |
| ③ 会话原始 usage 重算 | 同期同批 | ¥1.129 / 1.1634（含子代理） | `sessions/**/session.v4.jsonl.zstd` 的 `usage.{input,output,cacheRead,cacheWrite}Tokens` × 价目表 |

②与③只差约 0.9%，说明**计费公式与价目表彼此自洽**；①与②的差额是**记录覆盖/入账时点**问题，不是计价公式问题。10-23 覆盖 96.5%（4.07 vs 3.926242），10-24 在 01:01 时覆盖 78%（残差 0.32），复读后回到 97%（2.408/2.48），因此更像入账时点错位而非持续漏账。

## 口径判据（源码位置）

- `%USERPROFILE%\.dsh\profiles\desktop\node_modules\dsh-whale-widget\lib\index.js`
  - `BASE_PRICE = { hit:[0.02,0.04], miss:[1,2], out:[4,8] }`（:572），`PRO_PRICE = { hit:[0.15,0.3], miss:[4.5,9], out:[13.5,27] }`（:576），模型映射含 `deepseek-v4-pro`→PRO、`_default`→BASE（:578-582）；与 models.dev 折算的 ¥0.02/¥1/¥4 逐项一致。
  - 成本式：`(cache/1e6)*hit + (input/1e6)*miss + (outputBilled/1e6)*out`，峰桶 `isPeakTime(...)?1:0` 再取高档；峰谷判定用 `Math.floor(Date.now()/1000)`（**结算时刻而非请求时刻**），跨 09/12/14/18 点的轮次会出现 ±2 倍阶梯。
  - `appendUsageEvent({ts,model,cost,tokens})`（:932/:1507）写顶层 events，只有 `{ts,day,model,cost,tokens}`，**无 input/output/cache 拆分**。
  - `apiTodayUsage` 优先 `source:'balance'`（余额差），否则退回 `source:'events'`——**同一字段两种含义**，是跨口径误比的根源。
- `dsh-whale-widget/lib/accounting.mjs`：`observeBalance` 以 `lastUnits−units` 正向累加 `debitUnits`（全账户口径）；`partialDayOf` / `PARTIAL_GAP_MS=600000` **只测余额观测缺口、不测事件覆盖缺口**，故 10-24 被判 `partialDay=false` 而事件只到 01:01。
- `dsh-context/lib/index.js`：无价目表（`price` 0 命中），只累计 token 分类并从 `/user/balance` 取余额；`client.js` 用 models.dev 口径与 `Fi(e,t){return t==='cny'?e/.15:e}`（硬编码 1 CNY = 0.15 USD）。KPI 文案「已计价 {n}/{total} 个会话」「费用（仅含支持计价映射的模型）」表明其显示值是**下界**。

## 其他观察

- `.dshw-turn.json` 冻结在 `{"seq":20,"updatedAt":"2026-10-23T17:01:25.455Z"}`，不存金额，无法作为 0.71 的证据；后续新会话事件已恢复写入，属监听中断。
- 账本自身在分析期间持续变动（1.46→1.47→2.48，余额 100.47→100.46→99.45），任何图必须带快照时刻，否则旧图比新账必然对不上。
- 未验证：主程序 `app.asar` 本会话不可读；`/api/dsh-context/fleet` 返回 401；未取官方逐请求账单与 0.71 现场截图；未做色盲模拟实测；未联网核对 models.dev 挂牌价。

## 建议的下一步（一步定案）

1. 固定对账分母为「账户日扣费 vs 会话日志重算」两列，`events` 只作中间量；验收：复现 4.07/3.926242 与 1.46/1.163433。
2. 截图显示 0.71 的界面，**同一分钟**复制 `.dshw-usage.json`，记录当轮 `seq` 与时间。
3. 取 platform.deepseek.com 逐请求 usage，按 `ts` ±60s 与 `events[]` 匹配，定位残差归属（有记录/无记录两类），无记录部分 <5% 为通过。
4. 界面侧给「今日已用」标注口径来源（`balance`/`events`），并对 dsh-context 费用加「已计价 n/total」警示，禁止跨口径相减或双轴对比图。
